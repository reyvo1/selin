## The gap, measured before anything was written

Searched rather than assumed:

- **Zero `<img>` elements anywhere under `apps/`.** No `imageUrl`, `thumbnail` or `photo`.
- The POS product card rendered `<Package size={24}/>` — a Lucide icon in a 44×44 box.
- The storefront rendered `product.name.slice(0, 1).toUpperCase()` — **a single letter inside an
  `aspect-square` tile**. A page of products was a grid of initials.
- `model Product` has 28 fields and **none of them can hold a photo**. The only escape hatch is
  `metadata Json?`, which no app writes an image key to.
- The only image-ish fields in the whole schema belong to HR (`Employee.photoObjectKey`,
  `AttendancePhotoEvidence.thumbnailKey`). Nothing in commerce.

So this was not a rendering bug to be patched. The data model could not express the thing being asked
for, which is why it had to start at a migration.

## What research settled

Searched references on product-card and grid design. Three findings shaped the implementation:

1. A product photo is the **primary recognition cue** and should be the card's dominant element.
2. **One fixed aspect ratio across the grid**, or the eye re-learns the layout on every card.
3. **Explicit `width`/`height`, or reserved space** — otherwise images shove the rows below them as
   they load, and a re-flowing grid "feels broken no matter how polished the design".

A fourth, from the grid-density references: images are the heaviest element in a card, so a long
catalogue must not paint a hundred of them at once.

## What was built

**Model.** `imageUrl String?` added to `schema.prisma`, `schema.sqlite.prisma` and
`schema.postgresql.prisma`. Nullable, no default, no backfill.

**Migration.** `database/migrations/T360-20261015-product-imagery/` with `README.md`,
`postgresql-expand.sql` (with `IF NOT EXISTS`) and `sqlite-expand.sql` (without, which is the
documented engine asymmetry), registered last in `config/expand-migration-order.json`.

**Validation.** `apps/api/src/common/validation/is-http-image-url.ts`. `imageUrl` is the one product
field whose value reaches markup rather than a calculation, so it is treated as untrusted:

- only `http`/`https`; `javascript:`, `data:`, `blob:`, `file:`, `vbscript:` refused
- credentials in the authority refused — a card is public
- query strings refused — that is where a signed CDN token lives, and it publishes a credential
- whitespace, `<`, `>`, `"` refused; length capped at 2048
- **never fetched**, so it cannot probe internal hosts from the API
- empty string means "no photo", not a validation error

**Surfaces.** `apps/pos/app/product-media.tsx` — 4:3 box, `object-fit: cover`, `loading="lazy"`,
`decoding="async"`, falls back to the existing icon. `apps/storefront/app/product-photo.tsx` — replaces
the letter on the grid card, the compact card and the detail page, letter kept as fallback.
`apps/admin/app/modules/master-data.tsx` — a `URL foto produk` field.

The probe wrote with an Admin session and browsed with the cashier one. The first run used the cashier
token for both and got **403 on every write** — it had proved nothing. The probe clears the photo
afterwards so the local database is not left holding a dead `localhost` URL.

Two things the gates caught during the work, both of which would have shipped:

- The storefront **compact card** still rendered a bare initial. It differed from the grid card by one
  space in a `slice(0,1)` call, so the first replacement missed it. The "no surface is left rendering a
  bare letter" assertion is what found it.
- `tests/f12r2-modern-visual-contract.test.mjs` failed because it asserted the product card's Lucide
  icon by reading `page.tsx`. The icon moved into a component. The assertion was **retargeted, not
  weakened**: it now checks the card surface as a whole and additionally requires the `ProductMedia`
  call, so the icon contract still holds.

## What is NOT proven

- **PostgreSQL migration rehearsal has not run.** No PostgreSQL in this environment.
- **No GitHub workflow has run** against this source, and `uat:pre-github:local` was not run.
- **No human visual acceptance.** The photo was an SVG placeholder served from `apps/pos/public` and
  removed afterwards; nobody has judged how a real catalogue photograph actually looks at a till size.
- **No CDN, no upload path.** This ships a URL, not a file. Object storage is not built; the only
  precedent in the schema is `AttendancePhotoEvidence.objectKey`.
- Performance under a large real catalogue is reasoned about (`loading="lazy"`, fixed ratio) but not
  measured with real image weights.
