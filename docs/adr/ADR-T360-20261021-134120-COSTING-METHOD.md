# ADR T360-20261021-134120 — Costing engine dan valuasi persediaan

**Status:** ACCEPTED — disetujui 2026-10-21; implementasi dimulai.

**Date:** 2026-10-21

**Work item:** `T360-20261021-134120-costing-engine-dan-valuasi-persediaan`

## Context

Toko360 saat ini memakai `Product.costPrice` statis untuk COGS dan valuasi.
`InventoryMovement` hanya menyimpan kuantitas, bukan nilai; `InventoryBatch`
hanya menyimpan kuantitas batch. Penerimaan barang mencatat `unitCost` pada
`GoodsReceiptItem`, tetapi tidak membentuk layer biaya atau memperbarui
`Product.costPrice`. Akibatnya harga beli aktual dan COGS dapat berbeda.

Temuan source yang menjadi dasar:

- `Product.costPrice` wajib di `apps/api/prisma/schema.prisma:473`.
- `InventoryMovement` tidak memiliki biaya/layer di `schema.prisma:643-662`.
- COGS penjualan memakai `product.costPrice` di
  `apps/api/src/sales/sales.service.ts:1089` dan menyalin `unitCost` di
  `:1168`; movement dan FEFO ada di `:1251-1252`; jurnal HPP di `:1296-1305`.
- Penerimaan barang menambah stok dan batch di
  `apps/api/src/goods-receipts/goods-receipts.service.ts:318-338`, lalu
  memposting inventory/AP di `:359-361`, tanpa layer.
- Retur penjualan memakai biaya salinan dari sale di
  `apps/api/src/returns/returns.service.ts:434`, `:538`, `:550-556`.
- Transfer dan opname memakai `Product.costPrice` statis di
  `apps/api/src/advanced-inventory/advanced-inventory.service.ts:274`,
  `:339`, `:550`, `:584-586`.
- Valuasi dan margin report memakai `product.costPrice` di
  `apps/api/src/reports/reports.service.ts:658-695`, `:740`.
- `inventory.costing` belum ditegakkan di service mana pun; `FeatureFlag`
  hanya dibaca platform (`apps/api/src/platform/platform.service.ts:195-240`).
- Accounting core sudah idempotent dan menghormati period lock:
  `apps/api/src/accounting-core/accounting-core.service.ts:625-705`.

Keputusan user 21 Oktober 2026: metode HPP default **MOVING_AVERAGE**; FIFO dan
LIFO dapat dipilih sebagai policy. Average periodik tidak termasuk P0.

## Decision

### 1. Policy dan mode

Tambahkan `CostingPolicy` per company, dengan branch opsional:

- `method`: `MOVING_AVERAGE` (default), `FIFO`, atau `LIFO`.
- `mode`: `SHADOW` atau `ACTIVE`. Flag `inventory.costing` tetap menjadi
  gerbang fitur; flag OFF berarti jalur legacy.
- `effectiveFrom`, `version`, `status`, `approvedBy`, `approvedAt`.
- Metode tidak boleh diubah setelah ada `InventoryCostEvent` berstatus
  `POSTED`. Perubahan metode setelah go-live adalah rebuild/cutover terpisah
  dengan approval, bukan edit policy biasa.
- Satu scope aktif per company/branch. Scope memakai `scopeKey` non-null agar
  unique constraint konsisten di SQLite dan PostgreSQL.

### 2. Satu cost ledger, dua representasi

Semua mutasi biaya membuat `InventoryCostEvent` append-only. Representasi
penyimpanan mengikuti metode:

- **MOVING_AVERAGE:** `InventoryCostState` adalah sumber kebenaran per
  company/branch/warehouse/product/batch. Schema inventory saat ini tidak
  memisahkan stok per varian (`Inventory` dan `InventoryMovement` hanya memakai
  `productId`), sehingga costing varian ditunda sampai inventory mendukungnya.
  Penerimaan menambah `quantity` dan `value`; average = `value / quantity`.
  Pengeluaran memakai average saat itu. Tidak perlu layer per penerimaan. Saat
  `quantity = 0`, `value` wajib 0; residual pembulatan dibebankan ke event
  terakhir.
- **FIFO/LIFO:** `InventoryCostLayer` + `InventoryCostConsumption` adalah
  sumber detail. `InventoryCostState` tetap dipelihara sebagai agregat untuk
  locking, valuasi cepat, dan rekonsiliasi; nilainya wajib sama dengan jumlah
  layer.
- Batch-tracked product memakai scope per batch. Produk non-batch memakai
  sentinel batch kosong agar unique index tetap deterministik. Varian belum
  menjadi dimensi biaya pada P0.
- `InventoryCostEvent` menyimpan `quantityDelta`, `valueDelta`, `unitCost`,
  `balanceQuantity`, `balanceValue`, `method`, `occurredAt`, source identity,
  `operationKey`, `payloadHash`, dan status.

### 3. Alur biaya per mutasi

| Mutasi | Perilaku biaya |
|---|---|
| Goods receipt | Buat event RECEIPT dan layer/state pada `unitCost` net (ditambah pajak non-recoverable bila ada). Jangan mengubah `Product.costPrice`. |
| Sale/order | Buat event ISSUE; `SaleItem.unitCost`/`Sale.costTotal` dan `OrderItem.unitCost` berasal dari event. Jurnal HPP tetap lewat accounting core. |
| Sale return / order return | Kembalikan biaya COGS asli yang tersimpan pada konsumsi/ISSUE asal; FIFO/LIFO membuat restoration layer, average menambah `value` sebesar biaya asli. Retur order juga mengembalikan quantity batch asal. |
| Purchase return | FIFO/LIFO memakai layer asal; average memakai average saat ini. Saat ACTIVE, inventory dikreditkan sebesar carrying value; selisih terhadap harga beli (`net`) diposting ke akun variance `4203`/`5103` melalui accounting core, bukan edit layer. |
| Transfer | Source ISSUE pada biaya metode; destination RECEIPT pada biaya yang sama. Nilai in-transit dipertahankan; partial receipt memakai operation key per receipt. |
| Stock opname | Selisih negatif memakai biaya metode; selisih positif memakai average saat ini atau biaya eksplisit yang disetujui. Variance diposting lewat accounting core. |
| Produksi | Komponen ISSUE pada biaya metode; output RECEIPT pada total biaya komponen / qty output. Overhead/routing tetap di PKG-04. |
| Aset/maintenance | ISSUE pada biaya metode; jurnal mengikuti accounting core. |
| Opening stock | RECEIPT OPENING pada snapshot biaya yang disetujui; lihat ADR PKG-02. Opening juga wajib memperbarui location/condition balance dan `InventoryBatch` melalui jalur yang sama dengan receipt. |

### 4. Negative stock dan concurrency

- Saat costing ACTIVE, transaksi yang membuat on-hand negatif ditolak untuk
  produk yang tercakup costing, termasuk bila `Product.allowNegativeStock`
  true. Flag lama tidak boleh menjadi bypass integritas biaya.
- Semua mutasi berjalan dalam `serializableTx`. `InventoryCostState.version`
  dinaikkan dengan CAS `updateMany`; konflik memicu retry transaksi.
- FIFO/LIFO mengunci state row, mengambil layer `remainingQty > 0` sesuai
  urutan, lalu menulis consumption dan update layer. Tidak ada update layer
  di luar transaksi.
- Moving average tidak membaca seluruh layer; cukup state row. Ini menjaga
  performa pada volume besar.
- Pembulatan memakai Decimal(18,6) untuk unit cost dan Decimal(20,6) untuk
  value; residual pembulatan dibebankan ke komponen terakhir dan dicatat di
  event.

### 5. Idempotency

- `InventoryCostEvent` memiliki unique `(companyId, operationKey)` dan unique
  source identity `(companyId, sourceType, sourceId, sourceLineKey, eventType)`.
  `sourceLineKey` wajib string non-null (sentinel `''` untuk event tanpa baris)
  agar unique index tetap berlaku di SQLite dan PostgreSQL.
- Replay dengan key yang sama mengembalikan event lama. Key yang sama dengan
  payload berbeda ditolak `409`, bukan silent success.
- Operation key diturunkan dari dokumen sumber, misalnya
  `sale:<id>:<lineId>:issue`, `gr:<id>:<lineId>:receipt`,
  `sale-return:<id>:<lineId>:restore`.
- Event yang sudah POSTED tidak boleh dihapus. Koreksi memakai event reversal
  atau dokumen kompensasi.

### 6. Backdated dan tanggal efektif

- Cost event memakai tanggal sumber: `GoodsReceipt.receivedAt` untuk receipt,
  `Sale.occurredAt` untuk sale, tanggal opname/transfer/produksi untuk
  mutasi terkait.
- Tambahkan `InventoryMovement.occurredAt` (default `now`, backfill dari
  `createdAt`) agar laporan stok dapat memakai tanggal bisnis, bukan hanya
  `createdAt`. Writer baru wajib mengisi `occurredAt`.
- Posting ke periode tertutup ditolak accounting core. Cost event dan movement
  dalam transaksi yang sama harus rollback bila posting gagal.
- Backdated receipt hanya boleh memengaruhi layer/state dalam periode terbuka.
  Backdated receipt yang memiliki cost event lain setelahnya pada scope yang
  sama ditolak secara default karena akan mengubah COGS yang sudah diposting;
  koreksi memerlukan rebuild/cutover dengan approval dan jurnal kompensasi,
  bukan silent recalculation. Tidak ada recalculation historis di luar periode
  terbuka.

### 7. Schema minimum

Model baru (nama dapat disesuaikan saat implementasi, tetapi invariant tetap):

- `CostingPolicy`: `scopeKey`, `companyId`, `branchId?`, `method`, `mode`,
  `effectiveFrom`, `version`, `status`, `approvedBy`, `approvedAt`.
- `InventoryCostState`: company/branch/warehouse/product/batch dengan `branchId`
  non-null, `method`,
  `quantity`, `value`, `averageCost`, `version`, timestamps.
- `InventoryCostEvent`: company/branch/warehouse/product/batch (branch wajib,
  diturunkan dari warehouse),
  `movementId?`, `eventType`, `method`, `quantityDelta`, `valueDelta`,
  `unitCost`, `balanceQuantity`, `balanceValue`, `occurredAt`, source
  identity, `operationKey`, `payloadHash`, status.
- `InventoryCostLayer`: source event, `receivedAt`, `originalQty`,
  `remainingQty`, `unitCost`, `originalValue`, `remainingValue`, status.
- `InventoryCostConsumption`: layer, event, `quantity`, `amount`.
- `CostingRebuildRun`: scope, `fromDate`, `toDate`, status, checkpoint,
  statistics, approver, timestamps.

Semua tabel baru ada di tiga schema Prisma dan migration expand-only. Tidak
ada perubahan destruktif pada tabel lama. `InventoryMovement.occurredAt`
ditambahkan sebagai kolom nullable/default-safe dengan backfill.

### 8. Integrasi accounting

- Costing tidak membuat jurnal sendiri. Semua jurnal HPP, inventory, variance,
  dan transfer tetap melalui `postOperationalEvent`.
- Sale memakai nilai dari cost event untuk `cogs`, bukan `Product.costPrice`.
- Goods receipt memakai nilai layer/state untuk inventory debit.
- Retur supplier memakai nilai cost event dan memposting purchase price variance ke `4203` (gain) atau `5103` (loss); `PURCHASE-RETURN` v2 memakai amount key `inventory`.
- Retur, transfer, opname, produksi, dan aset memakai nilai cost event.
- Jika accounting posting gagal, seluruh transaksi stok dan biaya rollback.
- Posting rule yang ada dipertahankan; yang berubah hanya nilai dan source
  context.

### 9. API dan UI

API baru di inventory:

- `GET /inventory/costing/policies`, `POST /inventory/costing/policies`,
  `POST /inventory/costing/policies/:id/activate` (implementasi 2026-10-22;
  aktivasi memakai maker-checker dan `effectiveFrom` maju).
- `GET /inventory/costing/valuation` (implementasi 2026-10-22).
- `GET /inventory/costing/layers`, `GET /inventory/costing/reconciliation`
  (implementasi 2026-10-22; read-only, state vs Inventory, layer OPEN, dan
  saldo akun `1301` per branch; perbandingan GL dinonaktifkan bila filter
  produk/gudang aktif karena jurnal hanya memiliki dimensi branch).
- `POST /inventory/costing/rebuild` (implementasi 2026-10-22; membuat
  `CostingRebuildRun` PENDING untuk **backfill snapshot opening**, bukan replay

  memiliki cost event/state; maksimum 5.000 baris inventory per run.
- `POST /inventory/costing/rebuild-runs/:id/approve` (implementasi 2026-10-22;
  maker-checker, eksekusi sinkron dalam transaksi, mode SHADOW).
- `GET /inventory/costing/rebuild-runs`, `GET /inventory/costing/rebuild-runs/:id`
  (implementasi 2026-10-22; pagination dan status).

UI Admin:

- Pengaturan metode/mode, status approval, dan peringatan metode terkunci.
- Valuation/layer explorer dengan filter warehouse/product/batch.
- Reconciliation dashboard: state vs layer vs GL vs laporan.
- Rebuild/backfill status dan error.

POS tidak memerlukan UI baru; COGS berubah di belakang layar. Bila flag OFF,
seluruh endpoint costing disembunyikan dan jalur legacy tetap berjalan.

### 10. Backfill, shadow, dan aktivasi

1. Migration expand-only; deploy dengan flag OFF.
2. Backfill snapshot stok saat cutover: MOVING_AVERAGE membuat state; FIFO/LIFO
   membuat opening layer pada `Product.costPrice` snapshot.
3. Aktifkan mode SHADOW: event biaya dihitung dan dibandingkan dengan COGS
   legacy, tetapi COGS/jurnal masih legacy.
4. Rekonsiliasi: state/layer vs qty inventory vs GL vs report; selisih harus
   nol atau dijelaskan.
5. Setelah approval, aktifkan ACTIVE. Metode dikunci.
6. Monitor minimal satu siklus penjualan, retur, transfer, opname, dan tutup
   periode sebelum CLOSED.

Implementasi 2026-10-22 menjalankan langkah 2 sebagai backfill snapshot
`Inventory` saat approval, bukan rekonstruksi posisi pada `cutoverAt`: run
mencatat `cutoverAt` dan `snapshotAt`, dibatasi 5.000 baris, dan belum memiliki
checkpoint-resume atau jurnal opening. Karena itu backfill harus dijalankan
tepat pada cutover dan tidak boleh dianggap sebagai replay movement historis.

### 11. Rollback

- Matikan `inventory.costing`; sistem kembali ke jalur legacy tanpa menghapus
  tabel/event.
- Jika terjadi korupsi, hentikan write, restore snapshot, rebuild dari event
  sumber, dan rekonsiliasi.
- Posting yang sudah ACTIVE dibalik dengan reversal/compensating, bukan edit
  layer.
- Schema tetap ada; rollback tidak menjalankan drop table.

## Consequences

- Harga beli aktual akhirnya menjadi dasar COGS dan valuasi; purchase variance
  tidak lagi tersembunyi.
- Semua writer stok wajib memanggil costing service. Writer yang terlewat akan
  terdeteksi oleh reconciliation, tetapi tetap merupakan risiko implementasi.
- `Product.costPrice` tetap dipertahankan untuk kompatibilitas harga jual dan
  produk legacy; nilainya tidak lagi menjadi sumber COGS saat ACTIVE.
- Costing per varian belum didukung karena stock ledger belum menyimpan
  `variantId`; jangan menjanjikan HPP varian sampai migration inventory varian
  disetujui.
- Performa moving average terjaga karena hanya state yang dibaca; FIFO/LIFO
  membutuhkan index layer terbuka dan volume layer yang wajar.
- Metode terkunci setelah posting pertama; perubahan metode memerlukan
  rebuild/cutover terpisah.
- LIFO tetap disediakan sebagai policy operasional, tetapi penerapan pajak dan
  pelaporan LIFO harus disetujui finance/tax sebelum dipakai produksi.
- Payroll adjustment bypass di luar scope ADR ini; harus diperbaiki sebelum
  klaim year-end production-ready.

## Migration and rollback

Migration hanya menambah tabel/kolom/index. Backfill dijalankan sebagai job
terpisah dengan checkpoint dan dapat dilanjutkan. Baseline PostgreSQL
diregenerasi dan `db:baseline:postgres:check` wajib lulus. Rollback dilakukan
dengan flag OFF, bukan drop schema. Seluruh langkah diuji di SQLite dan
PostgreSQL dengan data sintetis.

## Security and operational impact

- Permission baru: `inventory.costing.view`, `inventory.costing.manage`,
  `inventory.costing.rebuild`.
- Policy/rebuild membutuhkan role finance/inventory yang sempit, approval
  maker-checker, audit event, dan tenant/branch/warehouse scope dari AuthUser.
- Tidak ada data kartu, token, biometric, atau data pribadi di cost layer.
- Monitoring: jumlah event/layer, layer kosong/negatif, selisih state vs layer
  vs GL, latency issue/valuation, kegagalan rebuild, dan umur layer terbuka.
- Alert bila selisih valuation/GL melewati ambang, rebuild gagal berulang, atau
  ada event tanpa movement.

## Test plan

- Unit: moving average receipt/issue, FIFO, LIFO, pembulatan, partial layer.
- Integration: receipt, sale, order, return, purchase return, transfer,
  opname, production, asset issue, opening.
- Concurrency: dua issue terakhir pada layer/state yang sama; retry tidak
  menggandakan COGS.
- Negative stock: transaksi ditolak atomik; tidak ada movement/jurnal parsial.
- Backdated: receipt dalam periode terbuka; periode tertutup menolak.
- Idempotency: replay operation key; payload berbeda ditolak.
- Reconciliation: state = layer = inventory qty = GL = report.
- Security: tenant isolation, permission, audit, maker-checker.
- Performance: valuation/issue pada volume besar; query plan dan index.
- Migration: SQLite/PostgreSQL rehearsal dan baseline check.

## Out of scope

- Average periodik, overhead/routing, WIP, dan HPP rakitan (PKG-04).
- Konsinyasi (PKG-12), komisi (PKG-05), cek/BG (PKG-07/08).
- Penerapan sync lintas node; costing event belum disinkronkan.
- Revaluasi pajak, multi-currency, dan laporan LIFO khusus pajak.
- Perbaikan payroll adjustment bypass; perlu work item terpisah.

## Implementation phases

Status 2026-10-22: fase 1–5 selesai diuji runtime; policy/valuasi, layer
explorer, FIFO/LIFO, backfill snapshot (state + opening layer), dan rekonsiliasi
Inventory/layer/GL selesai. Backfill memakai snapshot `Inventory` saat approval,
bukan replay movement; run dibatasi 5.000 baris dan eksekusinya sinkron.
Replay event historis dengan checkpoint/resume, jurnal opening, dan UI
pemilihan metode belum selesai. Retur pembelian FIFO/LIFO memprioritaskan layer
dari receipt event asal `goodsReceiptItemId`; bila layer asal sudah habis atau
tidak tersedia (mis. stok berasal dari opening backfill), konsumsi jatuh ke
urutan FIFO/LIFO. LIFO produksi tetap menunggu persetujuan finance/tax. Fase 6
(activation di TEST, performance, staging) belum selesai.
